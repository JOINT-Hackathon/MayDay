# 메이데이 개발·통합·시연 운영

> 기준일: 2026-11-14 · 현재 코드의 명령과 이후 작업 절차를 구분한다.

## 1. 작업 시작 전

1. `git status --short --branch`와 `git worktree list`로 브랜치·미커밋 파일·실제 작업 폴더를 확인한다. 이번 병렬 작업은 **여러 챗이 같은 `main` 작업 폴더를 공유**하고 있다. 따라서 파일 담당을 지키고, 한 담당이 작업 중인 파일은 통합 담당이 동시에 수정하지 않는다. 다음 병렬 작업에서 별도 worktree를 쓸 때는 공통 기준 커밋 또는 동일한 문서 전달이 먼저 필요하다.
2. [문서 안내](README.md), [제품 명세](../PRD-메이데이.md), [AI 명세](../AI-MVP-구현명세.md)를 읽는다.
3. 한 챗이 소유할 파일과 승인 기준을 정한다. 다른 챗의 파일을 수정해야 하면 변경 내용을 통합 담당에게 전달한다.

## 2. 병렬 챗 담당

| 작업 | 소유 파일 | 산출물 |
| --- | --- | --- |
| 화면·통합 | `src/App.jsx`, `src/styles.css`, `src/tokens.css`, `src/base.css`, 필요한 경우 `index.html`, 최종 `README.md` | 대화 없이 입력, AI 버튼, 저장·재조회, [디자인 시스템](DESIGN_SYSTEM.md) 적용, 통합 결과 |
| API | `server.mjs`, `.env.example` | 계약 확인, 실제 키가 있으면 샘플 호출 결과, 필요한 최소 수정 |
| 검증 | 기본적으로 읽기 전용 | [검증 계획](VALIDATION_QA.md)의 실행 결과와 재현 단계 |
| 제품 결정 | `PRD-메이데이.md`, `docs/ROADMAP.md`, `docs/DECISIONS.md` | 범위 변경과 이유 기록 |

이번에는 별도 worktree·브랜치가 생성되지 않았으므로 **브랜치 병합 단계가 없다.** 담당별 완료 보고와 파일 diff를 확인해 현재 작업 트리를 통합한다. 다음 병렬 작업부터는 별도 worktree와 `codex/` 브랜치를 우선 사용한다. 문서나 공통 파일을 두 챗이 동시에 편집하지 않는다. 리뷰 전에는 변경 파일, 실제 실행한 명령, 확인하지 못한 항목을 함께 보고한다.

### 새 챗에 바로 전달할 작업 지시

**API 챗**

**검증 챗**

## 3. 로컬 실행

`package.json` 기준 명령은 다음과 같다.

```bash
npm install
npm run dev
```

터미널에 표시된 주소를 사용한다. 현재 기본 개발 주소는 `http://127.0.0.1:5173`이다. 이미 포트를 사용 중이면 `PORT`를 조정하거나 실행 중인 프로세스를 확인한다.

AI를 시험할 때만 `.env.example`을 `.env`로 복사하고 **서버 환경 변수** `ANTHROPIC_API_KEY`를 넣는다. `.env`는 Git에서 제외된다. 실제 키를 문서·커밋·화면·로그에 넣지 않는다. 키가 없어도 수동 기능을 먼저 확인한다.

```bash
cp .env.example .env
npm run dev
```

## 4. 빌드·통합

```bash
npm run build
npm run preview
```

`preview`는 현재 `server.mjs`를 실행해 `dist/`와 API를 같은 주소에서 제공한다. 기본 실행 포트는 `4173`이다. 배포 환경에서 AI를 시연하려면 같은 출처의 API 서버와 서버용 키가 모두 필요하다. 정적 파일만 올리면 현재 `/api/organize`는 제공되지 않는다.

이번 통합 순서: 담당별 완료 보고 확인 → 공유 작업 트리의 파일 diff와 화면·API 계약 비교 → 충돌·잔여 문제 수정 → 고정된 코드에서 빌드 → [검증 계획](VALIDATION_QA.md)의 필수 흐름 → 최종 시연. 각 담당의 개별 테스트 통과를 **통합 결과의 통과**로 대신하지 않는다.

> 최신 버튼 이름·5분 대본·오류 시 전환은 [발표 가이드](PRESENTATION_GUIDE.md)를 우선합니다. 아래는 이전 짧은 폼 중심 순서입니다.

## 5. 3분 시연 순서

1. “경험을 다음 업무의 체크리스트 한 줄로 바꾼다”는 목적을 말한다.
2. 홈에서 실수 유형과 선택적 샘플 상황을 적고 **정리 시작하기**를 누른다. AI가 실제 검증된 환경이라면 동의 후 초안을 받아 사실·추측을 확인하고 수정한다. 아니면 수동 입력으로 진행한다.
3. 필수 두 칸을 채워 **두 트랙 저장하기**를 누르고 분석 결과에서 할 일 상세를 연다.
4. 체크리스트 팝업에서 항목을 선택해 적용 표시를 남긴다. 새로고침 후 같은 업무 종류에서 기록을 다시 찾는다.
5. 저장이 현재 브라우저에 한정되고 AI 결과는 사용자가 검토하는 초안임을 짧게 설명한다.

시연에는 실제 회사·고객 정보 대신 [AI 명세](../AI-MVP-구현명세.md#6-승인-기준)의 가상 문장을 사용한다. 실사용 성과, 자동 발송, 계정 동기화가 있는 것처럼 소개하지 않는다.

## 6. 시연 전 확인

- [ ] 현재 브랜치와 변경 파일을 확인했다.
- [ ] `npm run build`가 통과했다.
- [ ] AI 키 없는 수동 흐름이 저장·재조회까지 이어진다.
- [ ] AI를 시연한다면 실제 키로 성공 응답과 두 샘플의 사실성 검토를 마쳤다.
- [ ] 사용할 브라우저 프로필의 기존 기록과 포트 상태를 확인했다.
- [ ] 모바일·키보드·빈 기록·오류 안내를 확인했다.
- [ ] 발표 문구가 실제 구현과 검증 범위를 넘지 않는다.

검사 결과와 남은 위험은 [검증 계획](VALIDATION_QA.md)의 양식으로 남긴다.
